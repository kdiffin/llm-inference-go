Matrix multiplication & memory

Compute a dot product, map a matrix into a flat slice, then write and test a Go implementation.

dot productsmemory layoutGo exercise

1. Rows × columns

Imagine a workshop making two products. Each row of A describes the parts a product needs; each column of B describes a supplier’s prices. One output cell is the total cost for one product from one supplier.

Multiply each part count by its price, then add the results. This is a dot product. Matrix multiplication does this for every row–column pair.

Dot product explorerexplanatory model

Select an output cell in C. Underlined cells are participating in this step.

Cij = ∑k=0n−1 Aik Bkj

The shared dimension must match: an m × n matrix times an n × p matrix produces an m × p matrix. Each cell needs n multiplications and n − 1 additions when summing the products directly. A zero-initialized accumulator commonly executes n additions instead.

Check your understanding

C is 2 × 4. Each of its eight cells combines three products: one for every entry along the shared dimension. Compare with your answer.

2. Flat memory layout

A flat Go slice stores elements consecutively. In row-major order, the first row comes first, followed by the second row. The grid is a way we interpret the sequence.

Memory explorerhypothetical addresses

Hover, focus, or select a cell. Base address 0x1000 is invented. This model describes element storage, not Go’s slice header, caches, or allocation behavior.

To reach row i, skip i complete rows, each containing n elements. Then advance j elements into the row.

index := row*width + column
value := data[index]

The first line computes an element index; the second reads that element. Multiply the index by the element size only when reasoning about a byte offset—not when indexing a Go slice.

Check the indexing

In a 3-column matrix, why is (1, 0) at index 3 rather than index 1? Trace the three elements you pass before reaching the next row.

3. Implement it in Go

Implement experiments/matmul.go. Tests and a benchmark are provided; the multiplication function is left for you.

The contract

Implement Multiply(dst, a, b []float64, m, n, p int). Inputs are row-major A (m × n) and B (n × p). Overwrite dst (m × p); do not add to old values. Inputs and output do not overlap. Assume valid positive dimensions and exact slice lengths. Do not allocate inside the function or change the inputs.

Start with one output cell. Identify the row and column it needs. Only then generalize. Use the straightforward i–j–k ordering for this first experiment.

Hint 1 / what stays fixed?

While computing one output, its row in A and column in B stay fixed. Only the position along the shared dimension changes.

Hint 2 / two different widths

A has n columns. B and C have p columns. Apply the row-major rule separately to each matrix.

Hint 3 / where does the sum live?

Use a fresh accumulator for each output cell. Store it after visiting the shared dimension. Consider what happens if dst already contains nonzero values.

Run the tests

Run these from the repository root. The initial failure is deliberate: the kernel contains a TODO panic. The tests include rectangular shapes, negative values, input preservation, and repeated calls.

go test ./experiments -v

Run the benchmark

Before running: predict what happens to runtime if every dimension doubles. Record your reasoning in the notebook. Keep the machine otherwise quiet; record Go version, processor, power mode, and background activity.

go version
go env GOOS GOARCH
lscpu
go test ./experiments -run '^$' -bench BenchmarkMultiply -benchmem -count=5

ns/op means nanoseconds per complete multiplication, averaged over the benchmark’s timed iterations. B/op and allocs/op report allocation during that timed work. Setup allocations are outside the timer. Repeated runs expose variation; they do not eliminate bias.

What this first benchmark can—and cannot—tell you

The same input buffers are reused, so this is a repeated-buffer experiment. It is not a cold-memory latency test. CPU frequency, thermal state, compiler decisions, and other work can all affect timings. A timing difference alone does not identify a cache mechanism. Profiles and controlled experiments come later.
